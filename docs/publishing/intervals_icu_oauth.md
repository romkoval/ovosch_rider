# Intervals.icu: переход с API-ключа на OAuth (REQ-INT-01 крит. 5, ТЗ раздел 3, этап 8)

Сейчас (MVP) приложение работает по персональному API-ключу: пользователь вводит Athlete ID и ключ,
запросы идут с `Authorization: Basic base64("API_KEY:<ключ>")` (REQ-INT-01 крит. 1–3,
`src/integrations/intervals/`). Для публичного релиза ТЗ требует OAuth: пользователь не должен копировать
ключ из настроек Intervals.icu, а приложение не должно хранить ключ с полным доступом к аккаунту.

## 1. Что нужно согласовать с разработчиком Intervals.icu

Intervals.icu — сервис одного разработчика (David Tinker); OAuth-клиенты регистрируются **вручную**,
публичной формы саморегистрации нет. Канал — форум `https://forum.intervals.icu/`, раздел API
(тема «Intervals.icu API» / «OAuth for third party apps»), либо e-mail из раздела контактов сайта.

- [ ] Написать запрос на регистрацию OAuth-приложения. Указать:
      - название: `ovosch-rider`; краткое описание (тренировки на станке, чтение плана на день, FTP и зон);
      - ссылка на политику конфиденциальности (`docs/publishing/privacy_policy.md`, опубликованная версия) и на страницу приложения;
      - **redirect URI** (все, что будут использоваться):
        `http://127.0.0.1/callback` (loopback, порт динамический — уточнить, допускает ли сервер любой порт;
        если нет — зафиксировать порт, например `http://127.0.0.1:<PORT>/callback`),
        `ovoschrider://intervals` (iOS/Android custom scheme, по аналогии с Strava, В-6);
      - **scopes** (минимально необходимые, см. раздел 2);
      - логотип приложения (квадрат, PNG) — показывается на экране согласия.
- [ ] Получить `client_id` и `client_secret`. Записать способ хранения (раздел 3).
- [ ] Уточнить у разработчика: время жизни `access_token` (по обсуждениям на форуме токены Intervals.icu
      долгоживущие и refresh-токен может не выдаваться — тогда поток «обновление» заменяется повторным входом),
      лимиты запросов, допустимость динамического порта в redirect.
- [ ] Зафиксировать ответы в этом файле (раздел 5) и, при расхождении с планом, обновить требования через менеджера.

## 2. Эндпоинты, scope, поток

Значения на момент написания — по публичной документации `https://intervals.icu/api-docs.html` и форуму;
**сверить при регистрации**.

| Шаг | Значение |
| --- | --- |
| Authorization endpoint | `https://intervals.icu/oauth/authorize` |
| Token endpoint | `https://intervals.icu/api/oauth/token` |
| Параметры authorize | `client_id`, `redirect_uri`, `scope`, `state` (случайная строка, проверяется при возврате) |
| Параметры token | `client_id`, `client_secret`, `code`, `grant_type=authorization_code`, `redirect_uri` |
| Ответ token | `access_token`, `token_type=Bearer`, `scope`, `athlete` (объект с `id`, `name`), возможно `refresh_token`/`expires_at` |
| Использование | `Authorization: Bearer <token>` вместо `Basic`; базовый URL API без изменений |

Scope Intervals.icu — в верхнем регистре, через запятую:

| Scope | Нужен? | Зачем |
| --- | --- | --- |
| `CALENDAR:READ` | да | события календаря: запланированные тренировки на дату (REQ-INT-02, INT-04) |
| `SETTINGS:READ` | да | FTP, зоны мощности/пульса, вес атлета (REQ-INT-06) |
| `ACTIVITY:READ` | нет (MVP) | история активностей — не читаем |
| `ACTIVITY:WRITE` | нет (MVP) | выгрузка заездов в Intervals.icu — не предусмотрена ТЗ; добавить, если владелец решит дублировать выгрузку |
| `WELLNESS:*`, `LIBRARY:*`, `CALENDAR:WRITE`, `SETTINGS:WRITE` | нет | не требуются |

Запрашивать только `CALENDAR:READ,SETTINGS:READ` — минимальный scope упрощает согласование и ревью магазинов.

Поток в приложении (повторяет Strava, T-046): экран привязки → кнопка «Войти через Intervals.icu» → системный
браузер → согласие → redirect с `code` и `state` → обмен кода → `access_token` (+ `athlete.id` вместо ручного ввода Athlete ID)
в `SecureStore` под ключами `<profile_id>/intervals/access_token`, `.../refresh_token`, `.../expires_at`, `.../athlete_id`.
Ввод API-ключа остаётся как «расширенный» вариант для dev-сборок и до получения `client_id`
(обе схемы живут за одним интерфейсом клиента Intervals.icu; переключение — по наличию OAuth-конфигурации).

## 3. Хранение `client_secret`

Так же, как для Strava — решение **В-6** (`docs/backlog.md`, раздел решений; `docs/requirements.md` REQ-STR-01 крит. 6):
- в репозитории — только `secrets.example.cfg` с плейсхолдерами (добавить секцию `[intervals]`);
- dev-сборки — `user://secrets.cfg` или переменные окружения `OVOSCH_INTERVALS_CLIENT_ID` / `OVOSCH_INTERVALS_CLIENT_SECRET`;
- магазинные сборки — подстановка из конфигурации сборки вне репозитория;
- секрет не логируется и не попадает в тексты ошибок (аналог REQ-INT-01 крит. 2);
- альтернатива без секрета в клиенте — серверный обмен кода (владелец решает одновременно для Strava и Intervals.icu;
  один маленький сервис мог бы обслуживать оба redirect'а).
- Если разработчик Intervals.icu поддерживает публичных клиентов с PKCE (без секрета) — предпочесть этот вариант и отметить здесь.
