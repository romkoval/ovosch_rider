## Карточка

> Заголовок карточки до разделения: T-123 — Нативный модуль защищённого хранилища: Keychain macOS/iOS `[native-ble]` — `todo` — P0

Срез 0.5. Исполнитель — developer (зона нативных GDExtension). Размер M. Зависит: ответ на Н-28 (каталог вне `native/ble/`); bundle ID и подпись с Team ID (Apple Developer).
Почему не раньше (решение менеджера 2026-10-04, после «технические хвосты в приоритете»). Станок задаче не нужен, но: (1) сейчас артефакт macOS подписан ad-hoc и без sandbox — записи попадают в старый файловый login keychain, доступ к ним привязан к подписи, которая меняется с каждой сборкой CI: после каждого обновления macOS спросит у владельца пароль связки; (2) защищённая связка с `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (`docs/secure_store.md`) и sandbox (T-134) требуют подписи Team ID, а service = bundle id, которого ещё нет (`<BUNDLE_ID_PREFIX>`) — сделать сейчас значит сделать хранилище и миграцию дважды; (3) риск сейчас низкий: приложением пользуется только владелец, секреты в зашифрованном файле, внешние тестеры — в 0.6; (4) developer — единственный исполнитель 0.3. Что делаем раньше: вопрос Н-28 — requirements в волне 3 среза 0.3; если владелец получит Apple Developer и bundle ID до конца 0.3 и developer свободен — T-123 (macOS) и T-124 можно начать в паузах как P2.
Что сделать. По `docs/secure_store.md` разделы 2–3: `native/secure/` — `OvoschSecure`, контракт `secure_backend.h`, null-backend, Keychain-бэкенд на Security.framework (`kSecClassGenericPassword`, service = bundle id, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`); сборка macOS universal и iOS `xcframework` в CI; статическая сверка биндингов `test_native_secure_contract.gd`.
Закрывает: NFR-05 п.3 (Keychain), NFR-06 п.2 (по Н-28).
Критерии авто: CI собирает модуль для macOS и iOS; экспорт macOS грузит модуль; сверка биндингов с методами `SecureStore` зелёная. Ручные: NFR-05 п.4 (протокол T-127).
