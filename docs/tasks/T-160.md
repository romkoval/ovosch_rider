## Карточка

> Заголовок карточки до разделения: T-160 — Заезды на эмуляторе: метка в истории, без автовыгрузки в Strava `[game]` — `in-progress` (developer, worktree `wt-160`) — P1

Срез 0.3, вне волн, после T-154, до T-148. Исполнитель — developer. Размер S–M. Почему P1: с 0.3.0-preview.3 (T-150) владелец ездит на эмуляторе в release-сборке. Такие заезды в истории не отличить от настоящих, а после привязки Strava они уйдут в ленту владельца как настоящие тренировки. Сделать до того, как владелец привяжет Strava.
Что сделать.
1. Источник станка в метаданных заезда (`Ride`): эмулятор или реальное устройство, по возможности — имя устройства. Для тренировки и для свободной езды. Имя поля и значения — по Н-59. До ответа — по предложению (`trainer_source`: `ble` / `emulator`). Поле согласовать с будущим `trainer_mode` T-152 (`smart` / `power_meter` / `none`): источник и режим — разные оси, одно не дублирует другое.
2. Признак берётся через интерфейс `TrainerDevice` (например, «эмулятор: да/нет» в описании устройства), а не проверкой класса реализации: сессия знает интерфейс, а не реализацию (DEV-09 п.1, NFR-06 п.3). `FakeTrainer` — эмулятор, `BleTrainer` — нет.
3. История: в строке списка рядом с меткой режима «ПЛАН» / «SIM» (UIX-04 п.3) — метка «Эмулятор» / "Emulator" в стиле той же метки; в карточке заезда — та же метка. Вид — по `ui.md` (метки режима T-103); если места нет — сообщить game-designer, не выдумывать новый компонент.
4. Strava: заезд с источником «эмулятор» в очередь автоматически не ставится, статус — «не выгружен» (STR-05). Ручная выгрузка из карточки заезда (STR-04 п.5) — через диалог подтверждения («Заезд записан на эмуляторе, данные не настоящие. Выгрузить в Strava?» — опасное действие не по умолчанию, `DialogLayout`, UIX-01 п.8, 9); после подтверждения — в очередь как обычно.
5. Старые заезды без поля читаются без ошибок и считаются настоящими: угадывать источник задним числом нельзя. Если в метаданных старых заездов есть надёжный признак эмулятора (например, имя устройства в событиях), developer сообщает о нём в отчёте, но миграцию не делает без решения менеджера. Владельцу — удалить вручную тестовые заезды preview.3 до привязки Strava (раздел 4).
6. Переводы ru/en без переполнения (NFR-08, UIX-05 п.3).
Файлы: `src/devices/trainer_device.gd`, `src/devices/fake_trainer.gd` (признак), `src/session/{workout_session,free_ride_session}.gd` (или то место, где формируются метаданные заезда), `src/storage/ride.gd` (поле, совместимость), `src/integrations/strava/strava_service.gd` (`on_ride_saved`), `src/ui/history/{history_screen,ride_detail}.gd`, `assets/i18n/strings_menu.csv` (после T-154), `tests/`.
Закрывает: REQ-LOC-01 п.1 (новое поле — Н-59), REQ-STR-04 п.1 (исключение для эмулятора — Н-52 (а), Н-59), п.5 (подтверждение ручной выгрузки), REQ-UIX-04 п.3 (метка в строке истории); регрессия STR-05 п.1, 2, LOC-02 п.1, LOC-06 п.3, DEV-09 п.1, NFR-06, NFR-08. Ответы Н-52 и Н-59 работу не держат: developer делает по предложению.
Критерии авто:
- заезд на `FakeTrainer` (тренировка и свободная езда) сохраняется с источником «эмулятор», на станке через `StubBleBridge` — «реальное устройство»; поле переживает `save` → `get_ride`;
- профиль с привязкой Strava: заезд на эмуляторе → очередь пуста, статус «не выгружен»; заезд на станке → элемент очереди создан (регрессия T-049);
- ручная выгрузка заезда на эмуляторе: показан диалог; «Отмена» — очередь пуста; «Выгрузить» — элемент очереди создан;
- строка истории и карточка заезда на эмуляторе показывают метку, у обычного заезда метки нет;
- `meta.json` без поля читается без ошибки, заезд считается настоящим, автовыгрузка — как раньше;
- тест архитектуры зелёный (нет проверки класса реализации вне `src/devices/`); переводы ru/en без переполнения; полный прогон зелёный.
Ручная проверка — владелец на сборке с T-160 (раздел 4, «Замечания 0.3.0-preview.2»): заезд на эмуляторе с меткой в истории; при привязанной Strava он не выгружается сам; ручная выгрузка спрашивает подтверждение.
