## Карточка

> Заголовок карточки до разделения: T-116b — BLE-часть диагностического журнала `[game]` — `todo` — P0

Срез 0.4 (подготовка к сессии на Neo; делается в паузах 0.3, после T-108). Исполнитель — developer. Размер S–M. Зависит: T-116a.
Почему. У команды нет Tacx Neo; нативный BLE (T-021, T-022) никогда не работал с реальным станком. Единственный способ чинить его удалённо и сверять FTMS — журнал с машины владельца.
Что сделать.
1. События моста в журнал T-116a: скан, найденные устройства с сервисами и RSSI, подключение/обрыв с причиной, обнаружение сервисов, подписки; сырые пакеты `0x2AD2`, `0x2AD9`, `0x2ADA`, HRS, CSC, CPS в hex с меткой времени; ответы чтения `0x2ACC`, `0x2AD5`, `0x2AD6`, `0x2A19`; команды Control Point с метками отправки и ответа; границы интервалов (для NFR-01); переходы ERG / SIM / сопротивление; переподключения и восстановление цели.
2. Скрипт `scripts/dev/` для превращения журнала в фикстуры `tests/fixtures/ble/` (для T-119).
Сверка с T-154 (2026-10-04). События подключения датчиков уже пишет T-154 (срез 0.3): попытка, `connected`, сервисы, подписка, `error`, `disconnected` с причиной, переходы состояния. T-116b не дублирует их. Он берёт ту же категорию и те же точки записи и добавляет остальное из п.1 (пакеты в hex, станок, Control Point, ERG/SIM, переподключения).
Файлы: `src/devices/ble/` (журнал событий моста — платформенный слой, NFR-06 п.1), `src/session/` (только точки записи границ интервалов и переходов режимов), `scripts/dev/`, тесты.
Закрывает: инструмент для ручных критериев DEV-01 п.5, DEV-02 п.6, 7, FRD-04 п.10, NFR-01 п.3; регрессия NFR-05 п.1, NFR-06 п.1. REQ — Н-27.
Критерии авто: на `StubBleBridge` сценарий «скан → подключение → подписки → нотификации → Set Target Power → обрыв → переподключение» даёт журнал с событиями в правильном порядке и hex пакетов; задержка «граница интервала → запись Control Point» вычисляется из журнала; скрипт превращает журнал в фикстуру, которую разбирают кодеки T-016; поиск тестовых секретов пуст; тест архитектуры зелёный.
