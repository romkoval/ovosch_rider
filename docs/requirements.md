# ovosch-rider — реестр требований и критериев приёмки

Источник: `docs/tz.md` (ТЗ владельца продукта от 2 октября 2026, ред. 2 от 3 октября 2026 — графики HUD, свободная езда с SIM, трассы с рельефом, меню и экраны). Этот файл — единственный источник правды по тому, что считается готовым. Каждое требование разделов 5 и 6 ТЗ покрыто ровно одним REQ с тем же номером (PRF-01 → REQ-PRF-01). Область INF добавлена для инфраструктуры разработки.

## Кратко о продукте

Кроссплатформенное приложение для тренировок на умном велостанке Tacx Neo (BLE/FTMS). План на сегодня берётся из Intervals.icu или импортируется из ZWO/.erg/.mrc, тренировка проводится в ERG-режиме с HUD (график плана с фактом мощности и пульса) и 3D-визуалом дороги; без плана доступна свободная езда по одной из четырёх трасс с рельефом в SIM-режиме (уклон трассы задаёт сопротивление станка); заезд сохраняется локально, экспортируется в FIT и выгружается в Strava. Стек: Godot 4.7, GDScript, нативный BLE-модуль через GDExtension. Очерёдность платформ: iOS и macOS → Android → Linux и Windows.

Среда разработки и проверки: Linux-контейнер, Godot 4.7 headless, без macOS, без станка, без реальных аккаунтов. Поэтому критерии сетевых интеграций формулируются через поведение клиента на заданных HTTP-ответах, критерии BLE — через `FakeTrainer` и контракт нативного моста, критерии 3D — через headless-вычисления плюс ручная проверка визуала.

Термины: **план** — структурированная тренировка (последовательность шагов); **шаг/интервал** — элемент плана с длительностью и целью; **сессия** — текущее выполнение плана или свободной езды; **заезд** — сохранённый результат сессии; **сэмпл** — одна запись потоков данных за секунду; **трасса** — замкнутый маршрут с профилем высот h(s) по дистанции s и окружением; **свободная езда** — сессия без плана по выбранной трассе; **SIM** — режим, в котором станку передаётся уклон трассы (FTMS Set Indoor Bike Simulation Parameters, `0x11`); **крутизна** — доля уклона трассы (0–100 %), передаваемая станку в SIM.

Области REQ: INF — инфраструктура; PRF — профили; INT — Intervals.icu; IMP — импорт файлов; STR — Strava; DEV — устройства; WRK — проведение тренировки; HUD — экран тренировки; D3D — 3D-визуал и трассы; LOC — хранилище и история; FRD — свободная езда (раздел 5.10 ТЗ); UIX — меню и экраны приложения (раздел 5.11 ТЗ); NFR — нефункциональные.

## INF — инфраструктура разработки

### REQ-INF-01 — Автотесты GUT headless
**Формулировка.** Проект содержит набор автотестов GUT 9.7.1, запускаемый одной командой без GUI на Linux.
**Этап.** 1 (действует на всех этапах).
**Критерии приёмки.**
1. `./scripts/test.sh` при наличии Godot 4.7 (`GODOT=/path` или в PATH) запускает все тесты из `tests/unit/` и `tests/integration/` (конфигурация `.gutconfig.json`), завершается кодом 0 при успехе и ненулевым при любом падении. `[авто]`
2. `./scripts/test.sh -gselect=<имя_файла>` запускает один файл (фильтр по подстроке имени). `[авто]`
3. После запуска формируется JUnit-отчёт `tests/reports/results.xml`. `[авто]`
4. Тестовые файлы называются `test_*.gd`, наследуют `GutTest`, фикстуры лежат в `tests/fixtures/`. `[авто]`
5. Все тесты проходят без доступа к сети, станку и дисплею (`--headless`). `[авто]`

### REQ-INF-02 — CI на каждый пуш
**Формулировка.** GitHub Actions выполняет проверку открытия проекта и автотесты на каждый пуш в любую ветку и на каждый pull request. (Уже реализовано — `.github/workflows/ci.yml`.)
**Этап.** 1.
**Критерии приёмки.**

2. Шаг «Project opens headless» выполняет `godot --headless --path . --import` и падает при ошибках импорта. `[авто]`

## PRF — профили пользователей

### REQ-PRF-01 — Создание, переключение и удаление профилей
**Формулировка.** На одном устройстве можно создать несколько профилей, переключаться между ними и удалять их.
**Этап.** 1.
**Критерии приёмки.**
1. Создание профиля с именем (1–40 символов, непустое после обрезки пробелов) добавляет его в список; попытка создать профиль с пустым именем отклоняется с сообщением. `[авто]`
2. Имена профилей уникальны без учёта регистра; дубликат отклоняется. `[авто]` (допуск предложен, подтвердить)
3. Переключение активного профиля меняет текущий FTP, зоны, историю и список датчиков на данные выбранного профиля (проверяется по PRF-02, PRF-04). `[авто]`
4. Удаление профиля требует подтверждения; после подтверждения удаляются его заезды, токены и запомненные датчики; общий станок (PRF-04) остаётся. `[авто]` (объём удаления предложен, подтвердить)
5. Нельзя удалить последний оставшийся профиль; при попытке — сообщение. `[авто]` (допуск предложен, подтвердить)
6. Список профилей и активный профиль сохраняются между запусками приложения. `[авто]`

### REQ-PRF-02 — Собственные FTP, вес, зоны
**Формулировка.** У каждого профиля свои FTP, вес, зоны мощности и зоны пульса.
**Этап.** 1.
**Критерии приёмки.**
1. Профиль хранит FTP (целое, 50–600 Вт), вес (20.0–250.0 кг с шагом 0.1), максимальный пульс `max_hr` (целое, 100–220 уд/мин, по умолчанию не задан), границы зон мощности в % FTP и границы 5 зон пульса. Значения вне диапазона отклоняются с сообщением. `[авто]` (диапазоны FTP и веса предложены, подтвердить; `max_hr` — решение менеджера В-1, подтвердить владельцу)
2. По умолчанию зоны мощности — 7 зон Coggan: Z1 ≤55 %, Z2 56–75 %, Z3 76–90 %, Z4 91–105 %, Z5 106–120 %, Z6 121–150 %, Z7 >150 % FTP. `[авто]` (модель предложена, подтвердить)
3. По умолчанию зоны пульса — 5 зон от `max_hr` с границами 60/70/80/90 %: Z1 <60 %, Z2 60–69 %, Z3 70–79 %, Z4 80–89 %, Z5 ≥90 %; границы переопределяются вручную или из Intervals.icu (INT-06). `[авто]` (решение менеджера В-1, подтвердить владельцу)
4. Пока `max_hr` не задан и зоны пульса не переопределены, зоны пульса недоступны: функция зоны пульса возвращает «нет зоны», HUD-04 показывает «—». `[авто]` (решение менеджера В-1, подтвердить владельцу)
5. Изменение FTP в профиле A не меняет FTP профиля B. `[авто]`
6. Функция определения зоны при FTP 200 Вт даёт: 110 Вт → Z1, 111 → Z2, 150 → Z2, 151 → Z3, 180 → Z3, 181 → Z4, 210 → Z4, 211 → Z5, 240 → Z5, 241 → Z6, 300 → Z6, 301 → Z7. `[авто]`

### REQ-PRF-03 — Раздельные привязки Intervals.icu и Strava
**Формулировка.** У каждого профиля свои привязки Intervals.icu и Strava; токены хранятся раздельно в защищённом хранилище.
**Этап.** 6 (заготовка хранилища — этап 1).
**Критерии приёмки.**
1. Ключ API Intervals.icu и токены Strava записываются в `SecureStore` под ключами, включающими идентификатор профиля; запись для профиля A недоступна при чтении для профиля B. `[авто]` — через тестовую реализацию `SecureStore`.
2. Удаление привязки удаляет только записи этого профиля и этого сервиса. Отвязка Intervals.icu и Strava из настроек («Отвязать», UIX-04.3) выполняется только после подтверждения в диалоге UIX-01.8 (`docs/game/ui.md` п. 8.6): нажатие «Отвязать» в карточке интеграции открывает диалог и не меняет записей `SecureStore`; «Отмена», Esc или «назад» закрывают диалог — ключ/токены и статус привязки остаются прежними; удаление происходит только по опасной кнопке «Отвязать» в диалоге. `[авто]` (подтверждение отвязки — решение game-designer ред. 2, `ui.md` п. 13.1, и менеджера У-16, подтвердить владельцу)
3. Токены и ключи не встречаются в файлах данных профиля и заездов (`meta.json`, потоки, индексы) — проверка по содержимому файлов в `user://` после сохранения. `[авто]`
4. Реальная платформенная реализация (Keychain на macOS/iOS) хранит и возвращает значение после перезапуска приложения. `[вне контейнера]`

### REQ-PRF-04 — Своя история и свои датчики, общий станок
**Формулировка.** У каждого профиля своя история заездов и свой список запомненных датчиков; станок может быть общим для всех профилей.
**Этап.** 1 (история — этап 5).
**Критерии приёмки.**
1. Заезд, сохранённый в профиле A, не отображается в истории профиля B. `[авто]`
2. Датчик пульса, запомненный в профиле A, не предлагается к автоподключению в профиле B. `[авто]`
3. Запомненный станок доступен для автоподключения во всех профилях устройства. `[авто]`
4. Удаление профиля не удаляет общий станок из списка запомненных. `[авто]`

### REQ-PRF-05 — Выбор профиля при запуске
**Формулировка.** Если профилей больше одного, при запуске показывается экран выбора профиля.
**Этап.** 1.
**Критерии приёмки.**
1. При одном профиле экран выбора не показывается, профиль становится активным сразу. `[авто]`
2. При двух и более профилях стартовый экран — выбор профиля; главный экран недоступен, пока профиль не выбран. `[авто]` — проверка состояния навигации headless.
3. При отсутствии профилей показывается создание первого профиля. `[авто]`
4. Внешний вид экрана выбора. `[ручная проверка]`

## INT — Intervals.icu

### REQ-INT-01 — Авторизация по API-ключу; OAuth к публичному релизу
**Формулировка.** В MVP доступ по персональному API-ключу; к публичному релизу — OAuth.
**Этап.** 4 (API-ключ), 8 (OAuth).
**Критерии приёмки.**

2. Ключ сохраняется в `SecureStore` профиля (PRF-03), не логируется и не попадает в сообщения об ошибках (в тексте ошибки отсутствует подстрока ключа). `[авто]`
3. Ответ 401/403 на проверочный запрос даёт пользователю сообщение «ключ не принят» и не сохраняет ключ. `[авто]`
4. Проверка привязки на реальном аккаунте: после ввода ключа отображается имя атлета. `[ручная проверка]`
5. OAuth для публичного релиза: в `docs/publishing/intervals_icu_oauth.md` описаны шаги согласования доступа с разработчиком Intervals.icu, redirect URI и scope; реализация и проверка — `[вне контейнера]`.

### REQ-INT-02 — Тренировки из календаря на текущую дату
**Формулировка.** Приложение получает события календаря Intervals.icu за текущую дату.
**Этап.** 4.
**Критерии приёмки.**
1. Запрос событий ограничен текущей локальной датой устройства (`oldest` = `newest` = сегодня в формате `YYYY-MM-DD`). `[авто]`
2. Из ответа отбираются только события категории «тренировка» с велосипедным типом; события других категорий (заметки, гонки без плана, другие виды спорта) в список не попадают. `[авто]` — на фикстуре с смешанными событиями.
3. Пустой ответ (`[]`) приводит к состоянию «на сегодня тренировок нет» без ошибки. `[авто]`
4. Ответы 5xx и сетевая ошибка дают сообщение «не удалось загрузить план» с кнопкой «повторить»; приложение не падает. `[авто]`
5. Ответ 429 обрабатывается как временная ошибка с повтором не раньше чем через значение `Retry-After`; поддерживается форма в секундах (`Retry-After: 30` → 30 с); если заголовок задан HTTP-датой или отсутствует/не разбирается — 60 с. `[авто]` (допуск предложен, подтвердить)

### REQ-INT-03 — Разбор структурированной тренировки
**Формулировка.** Из события Intervals.icu извлекаются интервалы: длительность, целевая мощность (% FTP или ватты), целевой каденс, текстовые подсказки.
**Этап.** 4.
**Критерии приёмки.**
1. Шаг с длительностью и целью в % FTP преобразуется в шаг модели с длительностью в секундах и целью типа «% FTP» с сохранением числа (например, `10m 65%` → 600 с, 65 %). `[авто]`
2. Шаг с целью в ваттах даёт цель типа «ватты» (например, `5m 250w` → 300 с, 250 Вт). `[авто]`
3. Цель, заданная диапазоном (например, 60–70 %), преобразуется в середину диапазона (65 %). `[авто]` (правило предложено, подтвердить)
4. Рампа (начало → конец) сохраняется как шаг с начальной и конечной целью. `[авто]`
5. Повторы (`3x ...`) разворачиваются в плоскую последовательность шагов; количество шагов равно повторам × шагов в блоке. `[авто]`
6. Целевой каденс (rpm) переносится в шаг; при отсутствии — каденс «не задан». `[авто]`
7. Текстовое описание шага переносится как подсказка (HUD-08). `[авто]`
8. Суммарная длительность разобранного плана равна длительности, заявленной в событии (поле длительности ответа), с допуском ±1 с. `[авто]`
9. Неподдерживаемыми считаются только токены цели шага: цель по пульсу (`140bpm`, `70% hr`), зона как цель (`Z2`), темп (`4:30/km`), шаг без длительности (`press lap`). Такой токен приводит к ошибке разбора с указанием позиции; частично разобранный план не запускается. Свободные слова после валидной цели (например, `- 10m 65% Keep HR low`) — не ошибка: они становятся текстовой подсказкой шага (п.7). `[авто]` (решение менеджера В-15, подтвердить владельцу)

После успешной синхронизации без переопределения оба источника = `intervals:<дата синхронизации>`; после ручного изменения FTP или зон — `local`. `[авто]` (решение менеджера В-13, подтвердить владельцу)

7. На экране профиля виден источник значения: «из Intervals.icu (дата)» или «локально» (по `ftp_source`/`zones_source`). `[ручная проверка]`

### REQ-DEV-04 — Датчик каденса (CSC)

1. Уровень сопротивления задаётся в диапазоне 0–100 % с шагом 5 %; значение сохраняется в профиле между тренировками. `[авто]` (диапазон и шаг предложены, подтвердить)
2. Изменение уровня отправляет Set Target Resistance Level (`0x04`, uint8 в единицах 0.1, максимум кодируемого значения 25.5) не позже 1 с. Диапазон Supported Resistance Level Range читается после подключения через `read_characteristic(id, 0x1826, 0x2AD6)` (min, max, increment; sint16 LE в единицах 0.1; у Tacx Neo 0..100.0). Проценты пользователя 0–100 отображаются линейно на кодируемый поддиапазон `[max(min, 0); min(max, 25.5)]` с округлением к ближайшему кратному `increment`; 100 % → максимум кодируемого поддиапазона. Если `max` > 25.5 — одно предупреждение в лог (не ошибка пользователю). Без `0x2AD6` (нет характеристики или ответ не пришёл) — линейно 0..100 % → 0..25.5. Числа: при диапазоне 0..100.0 шаг 0.1 — 0 % → `04 00`, 50 % → 12.8 → `04 80`, 100 % → 25.5 → `04 FF`. `[авто]` (решение менеджера В-11, подтвердить владельцу)
3. При включённом ERG изменение уровня сохраняется, но не отправляется до выключения ERG. `[авто]`
4. На Tacx Neo изменение уровня ощущается при педалировании. `[ручная проверка]`

### REQ-WRK-05 — Пауза, возобновление, досрочное завершение
**Формулировка.** Тренировку можно поставить на паузу, возобновить и завершить досрочно.
**Этап.** 3.
**Критерии приёмки.**
1. Пауза останавливает таймер шага и общий таймер; тики во время паузы не продвигают план. `[авто]`
2. На паузе сэмплы не записываются в поток. В журнале событий заезда пауза фиксируется записью с полями `at_sec` (сессионное время начала паузы; само время паузы в сессионное не входит), `duration_sec` (реальная длительность паузы по часам устройства/тикам) и `until_sec = at_sec + duration_sec`; в метаданных заезда хранится `paused_total_sec` = Σ `duration_sec`. Тест: пауза на 120-й секунде длительностью 30 с → событие `{at_sec: 120, duration_sec: 30, until_sec: 150}`, `paused_total_sec: 30`, сэмплы продолжаются с t = 121. В FIT (LOC-05) пауза — `event timer stop_all` и `event timer start`; `total_elapsed_time` включает паузы, `total_timer_time` — нет. `[авто]` (решение менеджера D-6/Н-9, подтвердить владельцу)
3. Возобновление продолжает текущий шаг с того же остатка времени; на станок повторно уходит текущая цель (ERG) или уровень (не ERG) не позже 1 с. `[авто]`
4. Досрочное завершение требует подтверждения; заезд сохраняется с фактической длительностью и помечается «завершён досрочно». `[авто]`
5. На паузе исполнитель не отправляет на станок ничего (ни Set Target Power, ни Stop/Pause): целью станка остаётся последняя отправленная; журнал команд `FakeTrainer` за время паузы пуст. Телеметрия на паузе не записывается в поток (п.2), время паузы не входит в прошедшее время (HUD-05.2). При возобновлении текущая цель/уровень повторно отправляется не позже 1 с (п.3). `[авто]` (решение менеджера В-4, подтвердить владельцу)
6. Ощущение на Tacx Neo: при паузе нагрузка не меняется, после возобновления — соответствует цели интервала. `[ручная проверка]`

### REQ-HUD-07 — Полоса прогресса с профилем интервалов

Модель графика строится из модели сегментов HUD-07.1: для каждого шага — начало, длительность, цель в начале и в конце (для рампы разные), зона по цели с учётом множителя WRK-07; сумма длительностей равна длительности плана; шаг без цели (FreeRide) — сегмент без зоны с признаком «свободно». `[авто]`
2. Ось X: весь план целиком помещается в ширину графика при любой длине плана (скользящего окна нет) — x(0) = левый край, x(длительность плана) = правый край (±1 px); x(t) линейна по t. Ось Y мощности: от 0 до y_max = max(1.25 × максимальной цели плана с учётом множителя, 1.1 × FTP) — пунктир FTP всегда внутри поля графика; у плана без целей (только FreeRide/MaxEffort) y_max = 1.25 × FTP. Максимальная цель плана — наибольшая из целей в начале и в конце всех шагов (для рампы — большая из двух). Примеры при FTP 250 Вт: максимальная цель 150 Вт → y_max = 275 Вт; 300 Вт → 375 Вт; план без целей → 312.5 Вт (±0.5 Вт). При изменении множителя y_max и высоты сегментов пересчитываются не позже следующего сэмпла (1 с). Подписи оси мощности — только пунктир FTP на высоте y(FTP) ±1 px с подписью «FTP» и значением FTP профиля; других подписей ватт на графике нет. `[авто]` (решение менеджера по открытому решению 25 — по `docs/game/hud.md` п. 7; нижняя граница 1.1 × FTP и случай плана без целей — решение менеджера У-2; подтвердить владельцу)
3. Рампа (цель в начале ≠ цели в конце) — наклонный верх сегмента: высота в начале и в конце соответствует целям ±1 px; ровный шаг — горизонтальный верх. Рампа, цель которой пересекает границы зон, делится в модели на куски по точкам пересечения границ: число кусков = число зон, через которые проходит цель, каждый кусок — цвет своей зоны. 4. ### REQ-D3D-08 — Четыре трассы с рельефом и своим окружением
**Формулировка.** Несколько трасс с разным рельефом и окружением: равнина, холмы, горы, приморье; высота дороги в сцене соответствует профилю трассы. Решение владельца: трасс четыре — равнина (~10 км), холмы (~15 км), горы с длинным подъёмом (~20 км), приморье с рекой и мостом.

**Критерии приёмки.**

   - `flat`: L = 10.0 км, набор 19 м, макс. уклон 1.0 %;
   - `hills`: L = 15.0 км, набор 220 м, макс. уклон 7.5 %, ровно четыре подъёма;

### REQ-LOC-04 — Сводка заезда
**Формулировка.** Сводка: средняя и нормализованная мощность, средний пульс и каденс, работа в кДж, время в зонах.
**Этап.** 5.
**Критерии приёмки.**
1. Средняя мощность — среднее по сэмплам с данными (нули учитываются), округление до целого. `[авто]`
2. Уточнение: окна — только полные 30 с по сэмплам с данными мощности (строгий Coggan); если строгое значение на коротком или резко неравномерном потоке оказывается ниже средней, NP приравнивается средней. `[авто]` (решение менеджера В-16, подтвердить владельцу)
3. Работа = Σ P·1 с / 1000 кДж: 200 Вт в течение 3600 с → 720 кДж. `[авто]`
4. Средний пульс и каденс — по сэмплам с данными; каденс 0 учитывается, «нет данных» — нет. `[авто]`
5. Время в зонах мощности — секунды в каждой из 7 зон по зонам профиля на момент заезда; сумма равна числу сэмплов с данными мощности. Аналогично для 5 зон пульса; показание пульса 0 уд/мин считается отсутствием данных и не входит ни в счётчик сэмплов с пульсом, ни в среднее. `[авто]` (решение менеджера В-17)

## FRD — свободная езда

Решения владельца (ТЗ ред. 2, раздел 8): SIM-режим только в свободной езде, в тренировке по плану — ERG (WRK-02); свободная езда без ограничения по дистанции и времени, стоп вручную; заезд сохраняется и уходит в Strava как обычный; трасс четыре (D3D-08). Проверка в контейнере: `FakeTrainer` и журнал команд `StubBleBridge`, ускоренная симуляция через инъекцию часов (DEV-09.4).

**Команда SIM (FTMS Set Indoor Bike Simulation Parameters, Control Point `0x2AD9`).** Байты: `0x11`, затем Wind Speed (sint16 LE, м/с, разрешение 0.001), Grade (sint16 LE, %, разрешение 0.01), Crr — коэффициент сопротивления качению (uint8, разрешение 0.0001), Cw — коэффициент сопротивления ветру (uint8, кг/м, разрешение 0.01). Значения по умолчанию: ветер 0, Crr 0.004, Cw 0.20 кг/м (= 0.5 · 1.225 · 0.32, согласовано с моделью D3D-02). (решение менеджера по открытому решению 31, подтвердить владельцу)

**Модель скорости с уклоном.** Расширение модели D3D-02 на уклон: установившаяся скорость v из P = v · (m·g·(Crr·cos θ + sin θ) + 0.5·ρ·CdA·v²), θ = atan(g/100), m = вес профиля + 8 кг, CdA 0.32 м², Crr 0.004, ρ 1.225 кг/м³; на уклоне 0 совпадает с D3D-02. (модель предложена, подтвердить — открытое решение 15)

### REQ-FRD-03 — Превью трассы
**Формулировка.** Превью трассы: профиль высот по дистанции, длина, набор высоты, максимальный уклон.
**Этап.** 7.
**Критерии приёмки.**
1. Цифры превью вычисляются по профилю трассы теми же функциями, что в D3D-08 (длина, набор, макс. уклон), а не задаются вручную: для тестового профиля «1000 м ровно, 1000 м подъём на 50 м, 1000 м спуск на 50 м» превью даёт длину 3.0 км, набор 50 м, макс. уклон 5.0 % (±0.1 %). Тестовый профиль задаётся точками с шагом не больше 10 м, лежащими на этой ломаной (кусочно-линейный профиль: h = 0 м на s 0–1000 м, линейный рост до 50 м к s = 2000 м, линейный спад до 0 м к s = 3000 м), а не тремя-четырьмя опорными точками: интерполяция профиля между точками — периодическая PCHIP, и по редким точкам она дала бы другие набор и уклон. `[авто]` (решение менеджера У-6, подтвердить владельцу)
2. Формат: длина — км с одним знаком, набор — целые метры, макс. уклон — % с одним знаком; единицы на языке интерфейса (NFR-08). `[авто]`
3. Серия графика профиля высот: точки (s, h) по всему кругу, ось X — от 0 до L во всю ширину графика; ось Y — от min h трассы (нижний край поля) с размахом max(перепад трассы, 150 м) (`docs/game/tracks.md` п. 7), поэтому профиль занимает по высоте поля: `flat` 8 ± 2 %, `seaside` 30 ± 2 %, `hills` 65 ± 2 %, `mountains` 100 % (−2 %); число точек не больше 2 × ширины графика в пикселях с сохранением локальных минимумов и максимумов. `[авто]` (правило масштаба — по `tracks.md`, прореживание предложено, подтвердить)
4. На снимке экрана выбора трассы для каждой из четырёх трасс виден профиль высот, по форме различимый между трассами (на горах — длинный подъём во всю высоту, на равнине — почти плоская линия у дна), и три цифры с единицами; на карточке приморья под мостом отмечена вода. `[визуальная проверка]` — пункты U4, U8 чек-листа.
5. Заливка под профилем окрашена по уклону g(s) кусками палитры уклона (`docs/game/hud.md` п. 11): g < −2 % — сланец, −2…2 % — шалфей, 2…4 % — песок, 4…7 % — терракота, 7…10 % — кирпич, ≥ 10 % — вино; граница диапазона относится к более крутому по модулю подъёма (−2.0 % — шалфей, 2.0 % — песок, 10.0 % — вино; правило внутренних границ предложено, подтвердить); цвета профиля превью не совпадают с цветами зон мощности. Цифры карточек четырёх трасс совпадают с D3D-08.3: «10.0 км · 19 м · 1.0 %», «15.0 км · 220 м · 7.5 %», «20.0 км · 441 м · 9.4 %», «12.0 км · 56 м · 4.9 %» (с учётом допусков D3D-08.3). `[авто]`
6. ### REQ-FRD-04 — SIM-режим: уклон трассы на станок, скорость с уклоном
**Формулировка.** SIM-режим: уклон трассы в текущей точке передаётся станку (FTMS Indoor Bike Simulation), в подъём крутить тяжелее; скорость в сцене учитывает уклон, мощность и вес.
**Этап.** 7.
**Критерии приёмки.**
1. Кодек SIM формирует байты по формату из вводного абзаца FRD: уклон 5.00 % → `11 00 00 F4 01 28 14`; −3.00 % → `11 00 00 D4 FE 28 14`; 0 % → `11 00 00 00 00 28 14`; уклон 12.34 % → поле Grade `D2 04`; ветер 1.5 м/с → поле Wind Speed `DC 05`; Crr 0.004 → `28`; Cw 0.20 → `14`. Значения вне диапазона типов (уклон вне ±327.67 %, Crr > 0.0255, Cw > 2.55) кодеком отклоняются. `[авто]`
2. Передаваемый уклон = g(s) трассы в текущей позиции s (D3D-08), умноженный на крутизну FRD-05, округлённый до 0.01 %. Позиция s = интеграл скорости модели за время сессии (по модулю L). `[авто]`
3. Передаваемый уклон ограничивается диапазоном Supported Inclination Range (`0x2AD5`: min, max — sint16 LE, разрешение 0.1 %; increment — uint16), прочитанным после подключения через `read_characteristic(id, 0x1826, 0x2AD5)`; без ответа — диапазоном −10 … +20 %. `[авто]` (запасной диапазон предложен, подтвердить)
4. Ограничение частоты: команда `0x11` уходит не чаще одного раза в 1 с и только если передаваемый уклон отличается от последнего отправленного не меньше чем на 0.1 %; при езде 10 мин по трассе «горы» на `FakeTrainer` число команд `0x11` ≤ 600, между любыми двумя соседними ≥ 1000 мс. `[авто]` (частота и порог предложены, подтвердить)
5. Задержка: при въезде на участок с новым уклоном (изменение ≥ 0.1 %) команда уходит не позже 1 с после того, как позиция s пересекла границу участка (аналог NFR-01). После переподключения станка (DEV-08), возобновления после паузы и при старте сессии текущий уклон отправляется не позже 1 с, независимо от порога п.4. `[авто]`
6. Перед использованием SIM проверяется поддержка: в Fitness Machine Feature (`0x2ACC`) установлен бит «Indoor Bike Simulation Parameters Supported» Target Setting Features; если бит не установлен или станок отвечает на `0x11` кодом результата ≠ `0x01`, сессия переходит на фиксированное сопротивление (FRD-05.4) и на HUD свободной езды показывается сообщение «станок не поддерживает SIM» / «trainer does not support SIM»; сессия не прерывается. `[авто]` (решение менеджера по открытому решению 31, подтвердить владельцу)
7. Модель скорости с уклоном (вводный абзац FRD): v(P, m, g) монотонно растёт по P, убывает по g; на подъёме (g > 0) убывает по m. Опорные значения при 75 кг: 200 Вт, 0 % → как D3D-02.2 (34 ± 3 км/ч); 200 Вт, 5 % → 15.2 ± 1.5 км/ч; 200 Вт, 10 % → 8.4 ± 1.0 км/ч; 0 Вт, −5 % → установившаяся 49.8 ± 3 км/ч. Ограничение изменения за сэмпл и торможение — как D3D-02.3–4. `[авто]` (опорные значения выведены из модели, допуски предложены, подтвердить)
8. Модель скорости использует полный уклон трассы g(s), а не уклон, сниженный крутизной FRD-05 (крутизна влияет только на нагрузку станка). `[авто]` (решение менеджера по открытому решению 32, подтвердить владельцу)
9. Источник скорости в свободной езде — модель с уклоном (`speed_source = модель`), а не скорость станка: позиция на трассе, дистанция и уклон, отправляемый станку, согласованы между собой. `[авто]` (решение менеджера по открытому решению 33, подтвердить владельцу; отличие от В-8)
10. На Tacx Neo в подъём ощутимо тяжелее, на спуске легче; смена ощущается не позже 1–2 с после смены уклона в сцене. `[ручная проверка]`

### REQ-FRD-05 — Крутизна SIM и фиксированное сопротивление на лету
**Формулировка.** Настройка крутизны SIM (доля уклона, передаваемая станку, 0–100 %) и переключение на фиксированное сопротивление на лету.
**Этап.** 7.
**Критерии приёмки.**
1. Крутизна k задаётся от 0 до 100 % с шагом 5 %, по умолчанию 50 %, сохраняется в профиле между сессиями. Передаваемый уклон = g(s) × k / 100: при g = 8 % и k = 50 % уходит 4.00 % (`… 90 01 …`), при k = 0 % — 0 %, при k = 100 % — 8.00 %. Крутизна задаётся слайдером на экране выбора трассы (`docs/game/ui.md` п. 8.4) и в настройках («Тренировка», UIX-04.3). `[авто]` (значение по умолчанию 50 % — решение владельца 2026-10-03; шаг 5 % — предложен, подтвердить)
2. Крутизна применяется одинаково к подъёмам и спускам: при g = −4 % и k = 50 % уходит −2.00 %. `[авто]` (решение менеджера по открытому решению 32, подтвердить владельцу)
3. Изменение крутизны во время езды отправляет новый уклон не позже 1 с, даже если позиция на трассе не изменилась (обходя порог FRD-04.4, но не чаще 1 раза в 1 с). `[авто]`
4. Одно действие переключает SIM ↔ фиксированное сопротивление: при переходе на фиксированное не позже 1 с уходит Set Target Resistance Level с уровнем пользователя по правилу WRK-04.2 (тот же уровень и то же отображение процентов), после чего команд `0x11` нет до обратного переключения; при возврате в SIM не позже 1 с уходит `0x11` с текущим уклоном. Изменение уровня в фиксированном режиме — как WRK-04.2. `[авто]`
5. Переключение режима и изменение крутизны не останавливают таймер, не прерывают запись потоков и не меняют позицию на трассе; модель скорости в фиксированном режиме продолжает учитывать уклон (п.8 FRD-04). `[авто]`
6. Текущий режим (SIM/фиксированное) и крутизна видны на HUD свободной езды; каждое переключение записывается событием заезда (как переключения ERG, LOC-01.4). `[авто]`
7. На Tacx Neo изменение крутизны и переключение режима ощущаются при педалировании. `[ручная проверка]`

### Решения менеджера по вопросам В-1..В-9 (`docs/backlog.md`, раздел 5) — подтвердить владельцу
Решения приняты главным менеджером, чтобы не блокировать разработку; внесены в REQ с пометкой «(решение менеджера, подтвердить владельцу)». Владелец может отменить любое — тогда критерии правятся.

- **В-1** (PRF-02, HUD-04): поле профиля `max_hr`, валидация 100–220, по умолчанию пусто → зоны пульса недоступны, HUD-04 показывает «—»; зоны пульса по умолчанию — 5 зон от max HR (60/70/80/90 %), переопределяются вручную или из Intervals.icu.
- **В-2** (контракт моста, DEV-07, WRK-04, NFR-06): операция `read_characteristic(id, service_uuid, char_uuid)` с асинхронным ответом `characteristic_read(id, char_uuid, bytes)`; используется для Battery Level `0x2A19` и Supported Resistance Level Range `0x2AD6`.
- **Н-3** (вводный абзац DEV, DEV-01, 02, 06, 07, 08, 09, NFR-01, NFR-06): имена контракта моста согласованы с кодом `src/devices/ble/ble_bridge.gd` (`connect_peripheral`/`disconnect_peripheral`, `notification`, `write_done`, `error`, `discover_services`/`services_discovered`, `get_adapter_state`/`is_available`/`adapter_state_changed`); нативный класс `OvoschBle`, обёртка `NativeBleBridge`, заглушка `StubBleBridge`, выбор — `BleBridge.create_default()`. - **Н-2** (NFR-06.3): слои `src/session/` и `src/app/` признаны допустимыми с правилами зависимостей, зафиксированными в CLAUDE.md.
- **В-3** (LOC-01..07): **отклонение от ТЗ (SQLite)** — для MVP файловое хранилище за интерфейсом `RideRepository` (каталог заезда: `meta.json` + бинарные потоки); SQLite — допустимая реализация того же интерфейса позже; критерии через интерфейс, не через SQL.

### Уточнения по итогам волны 1 (ТЗ ред. 2) — решения менеджера, подтвердить владельцу
Решения оркестратора по вопросам, возникшим при реализации волны 1; внесены в критерии с пометкой «решение менеджера У-N, подтвердить владельцу». Владелец может отменить любое — тогда критерии правятся.

- **У-1** (HUD-07.1, HUD-10.5, HUD-11.1, HUD-12.1): после пропуска шага (WRK-06) курсор графика стоит в позиции плана — начало текущего шага + время, прошедшее в шаге, а не «прошедшее время / длительность плана»; без пропусков правила совпадают. Линии факта мощности и пульса строятся по той же позиции: сэмплы после пропуска сдвинуты на пропущенный остаток, над пропущенным остатком линии нет (разрыв). Модель полосы HUD-07 следует тому же правилу. Вопрос владельцу: так ли показывать пропуск — с «дырой» на графике и курсором, перескакивающим к следующему шагу?
- **У-2** (HUD-10.2): y_max = max(1.25 × максимальной цели с учётом множителя, 1.1 × FTP) — пунктир FTP всегда в поле графика; у плана без целей y_max = 1.25 × FTP. Подходит ли запас 1.1 × FTP для лёгких тренировок (восстановление на 50–60 % FTP)?
- **У-3** (NFR-06.1, NFR-06.3): `src/ui/` может зависеть от `UiScale`/`UiScaleRuntime` (`src/app/ui_scale.gd` — масштаб, безопасная зона, режим HUD/меню) наравне с `AppState`; нижние слои — нет. Тип устройства в `UiScale` определяется только через `DisplayServer`, без `OS.*` и литералов имён платформ, поэтому `ui_scale.gd` не входит в список исключений NFR-06.1.
- **У-4** (UIX-04.1): на главном экране (корень стека) системный «назад» Android сворачивает/закрывает приложение (штатное поведение Android), Esc на компьютере ничего не делает. Вопрос владельцу: нужен ли на Android запрос «Выйти?» или двойное нажатие для выхода (сейчас — нет)?
- **У-5** (D3D-05.4, D3D-07.1, D3D-08.6): бюджет MultiMesh — два числа `docs/perf_budget.md`: видимых экземпляров из любой точки трассы ≤ 2000 (`PerfBudget.MAX_VISIBLE_MULTIMESH_INSTANCES`, `max_visible_along`) — бюджет кадра; всего на трассе ≤ 40000 (`PerfBudget.MAX_MULTIMESH_INSTANCES`) — потолок памяти и построения. Итоговый FPS по-прежнему подтверждается ручной проверкой D3D-05.1 (эталонные устройства — открытое решение 16).
- **У-6** (FRD-03.1): тестовый профиль превью (3.0 км, набор 50 м, макс. уклон 5.0 %) задаётся кусочно-линейно точками с шагом ≤ 10 м, т.к. профиль трассы интерполируется периодической PCHIP и по редким опорным точкам дал бы другие цифры. Решение касается тестовых данных и на поведение продукта не влияет; подтвердить владельцу формально, вместе с остальными.

### Уточнения по итогам волн 2–4 (ТЗ ред. 2) — решения менеджера, подтвердить владельцу
