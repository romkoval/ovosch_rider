# ovosch-rider — реестр требований и критериев приёмки

Источник: `docs/tz.md` (ТЗ владельца продукта от 2 октября 2026, ред. 2 от 3 октября 2026 — графики HUD, свободная езда с SIM, трассы с рельефом, меню и экраны). Этот файл — единственный источник правды по тому, что считается готовым. Каждое требование разделов 5 и 6 ТЗ покрыто ровно одним REQ с тем же номером (PRF-01 → REQ-PRF-01). Область INF добавлена для инфраструктуры разработки.

## Кратко о продукте

Кроссплатформенное приложение для тренировок на умном велостанке Tacx Neo (BLE/FTMS). План на сегодня берётся из Intervals.icu или импортируется из ZWO/.erg/.mrc, тренировка проводится в ERG-режиме с HUD (график плана с фактом мощности и пульса) и 3D-визуалом дороги; без плана доступна свободная езда по одной из четырёх трасс с рельефом в SIM-режиме (уклон трассы задаёт сопротивление станка); заезд сохраняется локально, экспортируется в FIT и выгружается в Strava. Стек: Godot 4.7, GDScript, нативный BLE-модуль через GDExtension. Очерёдность платформ: iOS и macOS → Android → Linux и Windows.

Среда разработки и проверки: Linux-контейнер, Godot 4.7 headless, без macOS, без станка, без реальных аккаунтов. Поэтому критерии сетевых интеграций формулируются через поведение клиента на заданных HTTP-ответах, критерии BLE — через `FakeTrainer` и контракт нативного моста, критерии 3D — через headless-вычисления плюс ручная проверка визуала.

Термины: **план** — структурированная тренировка (последовательность шагов); **шаг/интервал** — элемент плана с длительностью и целью; **сессия** — текущее выполнение плана или свободной езды; **заезд** — сохранённый результат сессии; **сэмпл** — одна запись потоков данных за секунду; **трасса** — замкнутый маршрут с профилем высот h(s) по дистанции s и окружением; **свободная езда** — сессия без плана по выбранной трассе; **SIM** — режим, в котором станку передаётся уклон трассы (FTMS Set Indoor Bike Simulation Parameters, `0x11`); **крутизна** — доля уклона трассы (0–100 %), передаваемая станку в SIM.

Области REQ: INF — инфраструктура; PRF — профили; INT — Intervals.icu; IMP — импорт файлов; STR — Strava; DEV — устройства; WRK — проведение тренировки; HUD — экран тренировки; D3D — 3D-визуал и трассы; LOC — хранилище и история; FRD — свободная езда (раздел 5.10 ТЗ); UIX — меню и экраны приложения (раздел 5.11 ТЗ); NFR — нефункциональные.

## INF — инфраструктура разработки

### REQ-INF-01 — Автотесты GUT headless
**Формулировка.** Проект содержит набор автотестов GUT 9.7.1, запускаемый одной командой без GUI на Linux.
**Этап.** 1 (действует на всех этапах).
**Критерии приёмки.**
1. `./scripts/test.sh` при наличии Godot 4.7 (`GODOT=/path` или в PATH) запускает все тесты из `tests/unit/` и `tests/integration/` (конфигурация `.gutconfig.json`), завершается кодом 0 при успехе и ненулевым при любом падении. `[авто]`
2. `./scripts/test.sh -gselect=<имя_файла>` запускает один файл (фильтр по подстроке имени). `[авто]`
3. После запуска формируется JUnit-отчёт `tests/reports/results.xml`. `[авто]`
4. Тестовые файлы называются `test_*.gd`, наследуют `GutTest`, фикстуры лежат в `tests/fixtures/`. `[авто]`
5. Все тесты проходят без доступа к сети, станку и дисплею (`--headless`). `[авто]`

## PRF — профили пользователей

### REQ-PRF-01 — Создание, переключение и удаление профилей
**Формулировка.** На одном устройстве можно создать несколько профилей, переключаться между ними и удалять их.
**Этап.** 1.
**Критерии приёмки.**
1. Создание профиля с именем (1–40 символов, непустое после обрезки пробелов) добавляет его в список; попытка создать профиль с пустым именем отклоняется с сообщением. `[авто]`
2. Имена профилей уникальны без учёта регистра; дубликат отклоняется. `[авто]` (допуск предложен, подтвердить)
3. Переключение активного профиля меняет текущий FTP, зоны, историю и список датчиков на данные выбранного профиля (проверяется по PRF-02, PRF-04). `[авто]`
4. Удаление профиля требует подтверждения; после подтверждения удаляются его заезды, токены и запомненные датчики; общий станок (PRF-04) остаётся. `[авто]` (объём удаления предложен, подтвердить)
5. Нельзя удалить последний оставшийся профиль; при попытке — сообщение. `[авто]` (допуск предложен, подтвердить)
6. Список профилей и активный профиль сохраняются между запусками приложения. `[авто]`

### REQ-PRF-02 — Собственные FTP, вес, зоны
**Формулировка.** У каждого профиля свои FTP, вес, зоны мощности и зоны пульса.
**Этап.** 1.
**Критерии приёмки.**
1. Профиль хранит FTP (целое, 50–600 Вт), вес (20.0–250.0 кг с шагом 0.1), максимальный пульс `max_hr` (целое, 100–220 уд/мин, по умолчанию не задан), границы зон мощности в % FTP и границы 5 зон пульса. Значения вне диапазона отклоняются с сообщением. `[авто]` (диапазоны FTP и веса предложены, подтвердить; `max_hr` — решение менеджера В-1, подтвердить владельцу)
2. По умолчанию зоны мощности — 7 зон Coggan: Z1 ≤55 %, Z2 56–75 %, Z3 76–90 %, Z4 91–105 %, Z5 106–120 %, Z6 121–150 %, Z7 >150 % FTP. `[авто]` (модель предложена, подтвердить)
3. По умолчанию зоны пульса — 5 зон от `max_hr` с границами 60/70/80/90 %: Z1 <60 %, Z2 60–69 %, Z3 70–79 %, Z4 80–89 %, Z5 ≥90 %; границы переопределяются вручную или из Intervals.icu (INT-06). `[авто]` (решение менеджера В-1, подтвердить владельцу)
4. Пока `max_hr` не задан и зоны пульса не переопределены, зоны пульса недоступны: функция зоны пульса возвращает «нет зоны», HUD-04 показывает «—». `[авто]` (решение менеджера В-1, подтвердить владельцу)
5. Изменение FTP в профиле A не меняет FTP профиля B. `[авто]`
6. Функция определения зоны при FTP 200 Вт даёт: 110 Вт → Z1, 111 → Z2, 150 → Z2, 151 → Z3, 180 → Z3, 181 → Z4, 210 → Z4, 211 → Z5, 240 → Z5, 241 → Z6, 300 → Z6, 301 → Z7. `[авто]`

### REQ-PRF-03 — Раздельные привязки Intervals.icu и Strava
**Формулировка.** У каждого профиля свои привязки Intervals.icu и Strava; токены хранятся раздельно в защищённом хранилище.
**Этап.** 6 (заготовка хранилища — этап 1).
**Критерии приёмки.**
1. Ключ API Intervals.icu и токены Strava записываются в `SecureStore` под ключами, включающими идентификатор профиля; запись для профиля A недоступна при чтении для профиля B. `[авто]` — через тестовую реализацию `SecureStore`.
2. Удаление привязки удаляет только записи этого профиля и этого сервиса. `[авто]`
3. Токены и ключи не встречаются в файлах данных профиля и заездов (`meta.json`, потоки, индексы) — проверка по содержимому файлов в `user://` после сохранения. `[авто]`
4. Реальная платформенная реализация (Keychain на macOS/iOS) хранит и возвращает значение после перезапуска приложения. `[вне контейнера]`

### REQ-PRF-04 — Своя история и свои датчики, общий станок
**Формулировка.** У каждого профиля своя история заездов и свой список запомненных датчиков; станок может быть общим для всех профилей.
**Этап.** 1 (история — этап 5).
**Критерии приёмки.**
1. Заезд, сохранённый в профиле A, не отображается в истории профиля B. `[авто]`
2. Датчик пульса, запомненный в профиле A, не предлагается к автоподключению в профиле B. `[авто]`
3. Запомненный станок доступен для автоподключения во всех профилях устройства. `[авто]`
4. Удаление профиля не удаляет общий станок из списка запомненных. `[авто]`

### REQ-PRF-05 — Выбор профиля при запуске
**Формулировка.** Если профилей больше одного, при запуске показывается экран выбора профиля.
**Этап.** 1.
**Критерии приёмки.**
1. При одном профиле экран выбора не показывается, профиль становится активным сразу. `[авто]`
2. При двух и более профилях стартовый экран — выбор профиля; главный экран недоступен, пока профиль не выбран. `[авто]` — проверка состояния навигации headless.
3. При отсутствии профилей показывается создание первого профиля. `[авто]`
4. Внешний вид экрана выбора. `[ручная проверка]`

## INT — Intervals.icu

### REQ-INT-01 — Авторизация по API-ключу; OAuth к публичному релизу
**Формулировка.** В MVP доступ по персональному API-ключу; к публичному релизу — OAuth.
**Этап.** 4 (API-ключ), 8 (OAuth).
**Критерии приёмки.**
1. Пользователь вводит Athlete ID и API-ключ; каждый запрос содержит заголовок `Authorization: Basic base64("API_KEY:<ключ>")`. `[авто]` — проверка заголовка в моке транспорта.
2. Ключ сохраняется в `SecureStore` профиля (PRF-03), не логируется и не попадает в сообщения об ошибках (в тексте ошибки отсутствует подстрока ключа). `[авто]`
3. Ответ 401/403 на проверочный запрос даёт пользователю сообщение «ключ не принят» и не сохраняет ключ. `[авто]`
4. Проверка привязки на реальном аккаунте: после ввода ключа отображается имя атлета. `[ручная проверка]`
5. OAuth для публичного релиза: в `docs/publishing/intervals_icu_oauth.md` описаны шаги согласования доступа с разработчиком Intervals.icu, redirect URI и scope; реализация и проверка — `[вне контейнера]`.

### REQ-INT-02 — Тренировки из календаря на текущую дату
**Формулировка.** Приложение получает события календаря Intervals.icu за текущую дату.
**Этап.** 4.
**Критерии приёмки.**
1. Запрос событий ограничен текущей локальной датой устройства (`oldest` = `newest` = сегодня в формате `YYYY-MM-DD`). `[авто]`
2. Из ответа отбираются только события категории «тренировка» с велосипедным типом; события других категорий (заметки, гонки без плана, другие виды спорта) в список не попадают. `[авто]` — на фикстуре с смешанными событиями.
3. Пустой ответ (`[]`) приводит к состоянию «на сегодня тренировок нет» без ошибки. `[авто]`
4. Ответы 5xx и сетевая ошибка дают сообщение «не удалось загрузить план» с кнопкой «повторить»; приложение не падает. `[авто]`
5. Ответ 429 обрабатывается как временная ошибка с повтором не раньше чем через значение `Retry-After`; поддерживается форма в секундах (`Retry-After: 30` → 30 с); если заголовок задан HTTP-датой или отсутствует/не разбирается — 60 с. `[авто]` (допуск предложен, подтвердить)
6. Реальная загрузка плана на сегодня с аккаунта владельца. `[ручная проверка]`

### REQ-INT-03 — Разбор структурированной тренировки
**Формулировка.** Из события Intervals.icu извлекаются интервалы: длительность, целевая мощность (% FTP или ватты), целевой каденс, текстовые подсказки.
**Этап.** 4.
**Критерии приёмки.**
1. Шаг с длительностью и целью в % FTP преобразуется в шаг модели с длительностью в секундах и целью типа «% FTP» с сохранением числа (например, `10m 65%` → 600 с, 65 %). `[авто]`
2. Шаг с целью в ваттах даёт цель типа «ватты» (например, `5m 250w` → 300 с, 250 Вт). `[авто]`
3. Цель, заданная диапазоном (например, 60–70 %), преобразуется в середину диапазона (65 %). `[авто]` (правило предложено, подтвердить)
4. Рампа (начало → конец) сохраняется как шаг с начальной и конечной целью. `[авто]`

Диапазон Supported Resistance Level Range читается после подключения через `read_characteristic(id, 0x1826, 0x2AD6)` (min, max, increment; sint16 LE в единицах 0.1; у Tacx Neo 0..100.0). Проценты пользователя 0–100 отображаются линейно на кодируемый поддиапазон `[max(min, 0); min(max, 25.5)]` с округлением к ближайшему кратному `increment`; 100 % → максимум кодируемого поддиапазона. Если `max` > 25.5 — одно предупреждение в лог (не ошибка пользователю). Без `0x2AD6` (нет характеристики или ответ не пришёл) — линейно 0..100 % → 0..25.5. Числа: при диапазоне 0..100.0 шаг 0.1 — 0 % → `04 00`, 50 % → 12.8 → `04 80`, 100 % → 25.5 → `04 FF`. `[авто]` (решение менеджера В-11, подтвердить владельцу)
3. При включённом ERG изменение уровня сохраняется, но не отправляется до выключения ERG. `[авто]`
4. На Tacx Neo изменение уровня ощущается при педалировании. `[ручная проверка]`

### REQ-WRK-05 — Пауза, возобновление, досрочное завершение
**Формулировка.** Тренировку можно поставить на паузу, возобновить и завершить досрочно.
**Этап.** 3.
**Критерии приёмки.**
1. Пауза останавливает таймер шага и общий таймер; тики во время паузы не продвигают план. `[авто]`
2. На паузе сэмплы не записываются в поток. В журнале событий заезда пауза фиксируется записью с полями `at_sec` (сессионное время начала паузы; само время паузы в сессионное не входит), `duration_sec` (реальная длительность паузы по часам устройства/тикам) и `until_sec = at_sec + duration_sec`; в метаданных заезда хранится `paused_total_sec` = Σ `duration_sec`. Тест: пауза на 120-й секунде длительностью 30 с → событие `{at_sec: 120, duration_sec: 30, until_sec: 150}`, `paused_total_sec: 30`, сэмплы продолжаются с t = 121. В FIT (LOC-05) пауза — `event timer stop_all` и `event timer start`; `total_elapsed_time` включает паузы, `total_timer_time` — нет. `[авто]` (решение менеджера D-6/Н-9, подтвердить владельцу)
3. Возобновление продолжает текущий шаг с того же остатка времени; на станок повторно уходит текущая цель (ERG) или уровень (не ERG) не позже 1 с. `[авто]`
4. Досрочное завершение требует подтверждения; заезд сохраняется с фактической длительностью и помечается «завершён досрочно». `[авто]`
5. На паузе исполнитель не отправляет на станок ничего (ни Set Target Power, ни Stop/Pause): целью станка остаётся последняя отправленная; журнал команд `FakeTrainer` за время паузы пуст. Телеметрия на паузе не записывается в поток (п.2), время паузы не входит в прошедшее время (HUD-05.2). При возобновлении текущая цель/уровень повторно отправляется не позже 1 с (п.3). `[авто]` (решение менеджера В-4, подтвердить владельцу)
6. Ощущение на Tacx Neo: при паузе нагрузка не меняется, после возобновления — соответствует цели интервала. `[ручная проверка]`

### REQ-WRK-06 — Пропуск текущего интервала
**Формулировка.** Пользователь может пропустить текущий интервал.
**Этап.** 3.
**Критерии приёмки.**
1. Пропуск переводит исполнитель к следующему шагу на ближайшем тике; оставшееся время тренировки уменьшается на остаток пропущенного шага. `[авто]`
2. Новая цель уходит на станок не позже 1 с после пропуска. `[авто]`
3. Пропуск последнего шага завершает тренировку. `[авто]`
4. В заезде пропуск отмечается событием (номер шага, время). `[авто]`

### REQ-WRK-07 — Корректировка интенсивности на лету
**Формулировка.** Общий множитель интенсивности (например, 90 % или 110 %) меняется во время тренировки.
**Этап.** 3.
**Критерии приёмки.**
1. Множитель в диапазоне 50–150 % с шагом 5 %, по умолчанию 100 %. `[авто]` (диапазон и шаг предложены, подтвердить)
2. Множитель применяется ко всем целям (в % FTP и в ваттах): цель 200 Вт при 110 % → 220 Вт. `[авто]`
3. Изменение множителя в ERG отправляет новую цель не позже 1 с. `[авто]`
4. Целевая мощность на HUD (HUD-01) и профиль прогресса (HUD-07) отражают множитель. `[авто]`
5. Значение множителя сохраняется в заезде. `[авто]`

### REQ-WRK-08 — Сбор потоков 1 Гц
**Формулировка.** Потоки мощности, пульса, каденса, скорости и времени собираются с частотой 1 Гц.
**Этап.** 3.
**Критерии приёмки.**
1. Сэмплы записываются каждую секунду сессионного времени; метки времени монотонны с шагом 1 с; за 600 с активной тренировки записано 600 ± 1 сэмплов. `[авто]`
2. Сэмпл содержит: время (с от старта), мощность (Вт), пульс (уд/мин), каденс (rpm), скорость (км/ч), текущую цель (Вт), номер шага, флаг ERG; отсутствующие значения — «нет данных». `[авто]`
3. Если за секунду пришло несколько значений одного потока, в сэмпл попадает последнее. `[авто]` (правило предложено, подтвердить)
4. Если данные не приходили 5 с, значение источника — «нет данных» (не повторяется последнее). Для каденса датчики CSC/CPS выставляют «нет данных» раньше — через 3 с без пакетов (DEV-04.3, DEV-05.3, Н-4), чтобы `SensorHub` переключил источник до истечения общего порога. `[авто]` (допуск предложен, подтвердить)
5. Источник скорости: скорость станка из FTMS Indoor Bike Data, если станок передаёт поле скорости; иначе — расчётная по модели D3D-02. Выбор делается один раз при старте сессии и фиксируется в метаданных заезда как `speed_source` («станок»/«модель»); с `FakeTrainer` без поля скорости в сэмплы попадает расчётная скорость, с полем — скорость станка. То же значение идёт в FIT (LOC-05) и Strava (STR-02). `[авто]` (решение менеджера В-8, подтвердить владельцу)
6. Сбор идёт независимо от кадров отрисовки (NFR-02). `[авто]`

## HUD — экран тренировки

Проверка в контейнере: HUD-сцены инстанцируются headless, проверяются тексты узлов и вычисленные значения; визуальное оформление HUD-01..09 — `[ручная проверка]`, графики и раскладка HUD-10..14 — `[визуальная проверка]` по снимкам экрана тренировки. Референс раскладки и графиков HUD-10..14 — кадр Zwift Workout Mode `docs/game/shots/2026-10-03-reference/zwift_hud_workout.png` (план интервалов слева, график мощности и пульса внизу, ключевые цифры сверху); стиль (цвета, шрифт, формы) — решения game-designer в `docs/game/`.

Модели графиков (сегменты плана, точки факта, оси) проверяются headless как данные; отрисовка проверяется через свойства узлов и снимки. Геометрические критерии раскладки задаются в долях окна и проверяются на разрешениях 1280×720, 1920×1080, 2732×2048 (iPad), 2556×1179 (iPhone, альбомная). (набор разрешений предложен, подтвердить)

### REQ-HUD-01 — Целевая мощность крупно

### REQ-HUD-04 — Зона пульса

### REQ-HUD-05 — Пульс, каденс, скорость, время
**Формулировка.** Показываются пульс, каденс, скорость и прошедшее время.
**Этап.** 3.
**Критерии приёмки.**

3. Отсутствующее значение — «—». `[авто]`
4. Внешний вид. `[ручная проверка]`

### REQ-HUD-06 — Обратный отсчёт интервала
**Формулировка.** Обратный отсчёт до конца текущего интервала.
**Этап.** 3.
**Критерии приёмки.**
1. Значение = длительность шага − прошедшее время шага, формат `мм:сс`; на тике перехода показывается длительность нового шага. `[авто]`
2. За 5 с до конца шага состояние «скоро смена» (для визуального/звукового акцента). `[авто]` (допуск предложен, подтвердить)
3. Внешний вид. `[ручная проверка]`

### REQ-HUD-07 — Полоса прогресса с профилем интервалов
**Формулировка.** Полоса прогресса тренировки с профилем предстоящих интервалов, окрашенным по зонам.
**Этап.** 3.
**Критерии приёмки.**
1. Модель полосы: список сегментов (начало, длительность, цель Вт, зона); сумма длительностей равна длительности плана; позиция курсора = прошедшее время / общее время. `[авто]`
2. Зона сегмента пересчитывается при изменении множителя (WRK-07). `[авто]`
3. Пройденные сегменты помечены как пройденные; пропущенные (WRK-06) — как пропущенные. `[авто]`
4. Внешний вид. `[ручная проверка]`

**Связь с HUD-10 (ТЗ ред. 2).** Отдельная полоса прогресса на экране больше не обязательна: её роль выполняет график плана HUD-10 — профиль интервалов по зонам, курсор текущего момента и разделение пройденной/предстоящей части. Модель п.1–3 — та же модель сегментов, на которой строится HUD-10 (HUD-10.1–10.3 её расширяют, а не дублируют). П.4 принимается по HUD-10.7–10.8. Если на экране остаётся и отдельная полоса, и график, их сегменты и курсор должны совпадать (одна модель). Критерии п.1–3 остаются в силе.

### REQ-HUD-08 — Текстовые подсказки
**Формулировка.** Подсказки из плана показываются на экране.
**Этап.** 3.
**Критерии приёмки.**
1. Подсказка шага показывается с начала шага; подсказка с `timeoffset` — начиная с указанной секунды шага. `[авто]`
2. Подсказка исчезает через 10 с или при смене шага. `[авто]` (допуск предложен, подтвердить)
3. Текст показывается как есть, без обрезки до 120 символов; длиннее — обрезается с «…». `[авто]` (допуск предложен, подтвердить)
4. Внешний вид. `[ручная проверка]`

### REQ-HUD-09 — Сглаживание мощности 3 с
**Формулировка.** Отображаемая мощность сглаживается за 3 секунды.
**Этап.** 3.
**Критерии приёмки.**
1. Сглаженное значение = среднее арифметическое последних 3 сэмплов мощности (1 Гц), округлённое до целого; для последовательности 100, 200, 300 → 200; затем 300 → 267. `[авто]`
2. Пока сэмплов меньше 3 — среднее доступных. `[авто]`
3. Сэмплы «нет данных» исключаются из среднего; если все три — «—». `[авто]`
4. Сглаживание влияет только на HUD; в поток WRK-08 и в FIT пишутся несглаженные значения. `[авто]`

### REQ-HUD-10 — График плана во всю ширину низа экрана
**Формулировка.** График плана: профиль интервалов во всю ширину нижней части экрана, окрашенный по зонам, с мягкими формами и шкалой времени; пройденная часть отделена от предстоящей. Заменяет по смыслу полосу прогресса HUD-07 (см. связь в HUD-07).
**Этап.** 7.
**Критерии приёмки.**
1. Модель графика строится из модели сегментов HUD-07.1: для каждого шага — начало, длительность, цель в начале и в конце (для рампы разные), зона по цели с учётом множителя WRK-07; сумма длительностей равна длительности плана; шаг без цели (FreeRide) — сегмент без зоны с признаком «свободно». `[авто]`
2. Ось X: весь план целиком помещается в ширину графика — x(0) = левый край, x(длительность плана) = правый край (±1 px); x(t) линейна по t. Ось Y мощности: от 0 до y_max = 1.25 × максимальной цели плана с учётом множителя; при изменении множителя y_max и высоты сегментов пересчитываются не позже следующего сэмпла (1 с). `[авто]` (коэффициент 1.25 предложен, подтвердить)
3. Рампа (цель в начале ≠ цели в конце) — наклонный верх сегмента: высота в начале и в конце соответствует целям ±1 px; ровный шаг — горизонтальный верх. `[авто]`
4. Шкала времени: подписи кратны шагу — наименьшему из ряда 1, 2, 5, 10, 15, 30, 60 мин, при котором подписей (включая 0) не больше 10; для плана 60 мин — шаг 10 мин (подписи 0, 10, …, 60), для плана 20 мин — шаг 5 мин (формат подписи — минуты, от часа — `ч:мм`). `[авто]` (ряд и число подписей предложены, подтвердить)
5. Курсор текущего момента: x = прошедшее время / длительность плана × ширина (±1 px), обновляется каждый сэмпл; на паузе не двигается. Пройденная часть (левее курсора) и предстоящая имеют разные состояния отрисовки в модели (`пройдено`/`предстоит`); пропущенный шаг (WRK-06) имеет состояние `пропущено`. `[авто]`
6. Цвет сегмента берётся из палитры зон HUD-03.2 по зоне сегмента; сегмент «свободно» — нейтральный цвет, не цвет зоны. `[авто]` — проверка токена цвета в модели.
7. На снимке экрана тренировки (план не короче 30 мин, состояния: начало, середина, последний интервал) график занимает всю ширину нижней части экрана; видно не меньше двух разных цветов зон; верхние углы сегментов скруглены (нет прямоугольных «ступенек» с острыми углами); пройденная часть визуально отличается от предстоящей (затемнена/приглушена); шкала времени читается. `[визуальная проверка]`
8. На устройстве график читается с расстояния 1.5 м. `[ручная проверка]`

### REQ-HUD-11 — Линия фактической мощности поверх плана
**Формулировка.** Поверх графика плана рисуется линия фактической мощности (сглаженной) за прошедшее время.
**Этап.** 7.
**Критерии приёмки.**
1. Серия факта — одна точка (t, P) на каждый записанный сэмпл, где P — сглаженная мощность HUD-09 на этом сэмпле; x и y — в тех же осях, что и план (HUD-10.2). Для потока 100, 200, 300, 300 Вт с t = 1..4 серия содержит точки со значениями 100, 150, 200, 267. `[авто]`
2. Новая точка появляется в серии не позже следующего сэмпла (1 с); точек правее курсора HUD-10.5 нет. `[авто]`
3. Сэмпл «нет данных» мощности даёт разрыв линии (серия делится на отрезки), а не точку 0. Пауза (WRK-05) не добавляет точек; после возобновления линия продолжается с того же x. `[авто]`
4. Значение выше y_max рисуется на верхней границе графика (точка не выходит за пределы области графика) и помечено в модели как обрезанное. `[авто]` (правило предложено, подтвердить)
5. Число точек серии, передаваемых на отрисовку, не больше 2 × ширины графика в пикселях; при прореживании в каждой корзине сохраняются минимум и максимум (как LOC-03.2). Для плана 3 ч на графике шириной 1280 px — не больше 2560 точек, пиковая мощность 30-секундного спринта присутствует среди точек. `[авто]` (допуск предложен, подтвердить)

### REQ-HUD-12 — Пульс красной линией без заливки со своей шкалой
**Формулировка.** Пульс выводится на том же графике одной красной линией без заливки, со своей шкалой.
**Этап.** 7.
**Критерии приёмки.**

4. Цвет линии — один токен палитры «пульс», красного тона (оттенок HSV в диапазоне 345–15°, насыщенность ≥ 0.6); один и тот же цвет на всей длине, независимо от зоны пульса. `[авто]` (диапазон тона предложен, подтвердить; конкретный цвет — game-designer)

### REQ-D3D-07 — Стилизованный мир по референсу владельца
**Формулировка.** Мир заезда переработан под референс владельца (видео 2026-10-03, кадры — `docs/game/shots/2026-10-03-reference/`): «нарисованный» стиль — тун-свет в два тона с холодной тенью, тёмный контур, тёмный асфальт с белой разметкой, бордюр, трава, отбойник, человек на шоссейном велосипеде, наклон в поворотах. **Этап.** 7.
**Критерии приёмки.**
1. По трассе строится мир: дорога с разметкой (шейдер, не сплошной цвет), обочина с бордюром и полосой травы, рельеф до горизонта с холмами на краю, не меньше трёх типов растительности плюс сигнальные столбики; число узлов, материалов, источников света и экземпляров MultiMesh — в бюджете `docs/perf_budget.md`; выключение частей мира в `EnvironmentSet` не ломает сцену. `[авто]`

### REQ-D3D-08 — Четыре трассы с рельефом и своим окружением
**Формулировка.** Несколько трасс с разным рельефом и окружением: равнина, холмы, горы, приморье; высота дороги в сцене соответствует профилю трассы. Решение владельца: трасс четыре — равнина (~10 км), холмы (~15 км), горы с длинным подъёмом (~20 км), приморье с рекой и мостом.
**Этап.** 7.
**Критерии приёмки.**
Профиль трассы — функция высоты h(s), м, по дистанции s ∈ [0; L], заданная точками не реже чем через 10 м. Вычисляемые характеристики (используются здесь и в FRD-03): **длина** L; **набор высоты** — сумма положительных приращений h по точкам профиля за один круг; **уклон** g(s) = Δh/Δs по скользящему окну 100 м, в %; **максимальный уклон** — максимум g(s) за круг. (шаг точек и окно уклона предложены, подтвердить)
1. Каталог трасс содержит ровно четыре трассы с уникальными идентификаторами `flat`, `hills`, `mountains`, `seaside` (имена — подсказка, не требование), у каждой — название на ru и en, профиль высот и ссылка на набор окружения. `[авто]`
2. Каждая трасса замкнута: |h(L) − h(0)| ≤ 0.1 м, разрыв уклона на стыке круга ≤ 1 % (уклон по окну 100 м, переходящему через стык); горизонтальная геометрия дороги на стыке непрерывна (D3D-03). `[авто]` (допуски предложены, подтвердить)
3. Характеристики профилей — вычисляются по профилю в тесте. `[авто]` (все диапазоны предложены, подтвердить — см. открытое решение 29)
   - равнина: L = 10 км ± 10 %, набор ≤ 60 м, макс. уклон ≤ 2 %;
   - холмы: L = 15 км ± 10 %, набор 150–350 м, макс. уклон 4–8 %, не меньше трёх отдельных подъёмов (участков с g > 2 % длиной ≥ 300 м);
   - горы: L = 20 км ± 10 %, есть непрерывный подъём длиной ≥ 5 км со средним уклоном ≥ 5 %, набор ≥ 400 м, макс. уклон ≤ 12 %;
   - приморье: L = 8–15 км, набор ≤ 150 м, макс. уклон ≤ 6 %; в профиле есть участок моста над рекой (отмечен в данных трассы диапазоном s).
4. Высота дороги в сцене соответствует профилю: для точек s с шагом 50 м по всему кругу высота оси дороги и позиция велосипедиста по вертикали равны h(s) ± 0.05 м; рельеф окружения не поднимается выше полотна дороги в пределах её ширины (дорога нигде не «утоплена» в землю). `[авто]` (допуски предложены, подтвердить)
5. Велосипедист и камера на уклоне: продольный наклон велосипедиста равен atan(g(s)/100) ± 1°; требования к камере D3D-07.5 (горизонтальное расстояние ±0.05 м, велосипедист в кадре) выполняются на всех точках п.4, включая максимальный уклон и переход подъём → спуск. `[авто]` (допуск предложен, подтвердить)
6. Окружения различаются составом: у каждой трассы свой набор окружения; на приморье есть водная поверхность (море и/или река) и мост, по которому идёт дорога на участке п.3; на горах рельеф горизонта выше, чем на равнине. По снимкам каждой трассы (дистанции — начало, середина подъёма, вершина или мост, спуск; конкретные s задаются по профилю) чек-лист `ride-visual-review` — не меньше 10 из 12 без блокирующих пунктов на каждом кадре; на кадрах подъёма дорога видимо уходит вверх, на кадрах спуска — вниз; четыре трассы различимы по кадру без подписи (равнина — плоский горизонт, холмы — волнистый, горы — высокие склоны, приморье — вода и мост в кадре). `[визуальная проверка]`

### REQ-LOC-04 — Сводка заезда
**Формулировка.** Сводка: средняя и нормализованная мощность, средний пульс и каденс, работа в кДж, время в зонах.
**Этап.** 5.

## FRD — свободная езда

Решения владельца (ТЗ ред. 2, раздел 8): SIM-режим только в свободной езде, в тренировке по плану — ERG (WRK-02); свободная езда без ограничения по дистанции и времени, стоп вручную; заезд сохраняется и уходит в Strava как обычный; трасс четыре (D3D-08). Проверка в контейнере: `FakeTrainer` и журнал команд `StubBleBridge`, ускоренная симуляция через инъекцию часов (DEV-09.4).

**Команда SIM (FTMS Set Indoor Bike Simulation Parameters, Control Point `0x2AD9`).** Байты: `0x11`, затем Wind Speed (sint16 LE, м/с, разрешение 0.001), Grade (sint16 LE, %, разрешение 0.01), Crr — коэффициент сопротивления качению (uint8, разрешение 0.0001), Cw — коэффициент сопротивления ветру (uint8, кг/м, разрешение 0.01). Значения по умолчанию: ветер 0, Crr 0.004, Cw 0.20 кг/м (= 0.5 · 1.225 · 0.32, согласовано с моделью D3D-02). (параметры предложены, подтвердить — открытое решение 31)

**Модель скорости с уклоном.** Расширение модели D3D-02 на уклон: установившаяся скорость v из P = v · (m·g·(Crr·cos θ + sin θ) + 0.5·ρ·CdA·v²), θ = atan(g/100), m = вес профиля + 8 кг, CdA 0.32 м², Crr 0.004, ρ 1.225 кг/м³; на уклоне 0 совпадает с D3D-02. (модель предложена, подтвердить — открытое решение 15)

### REQ-FRD-04 — SIM-режим: уклон трассы на станок, скорость с уклоном
**Формулировка.** SIM-режим: уклон трассы в текущей точке передаётся станку (FTMS Indoor Bike Simulation), в подъём крутить тяжелее; скорость в сцене учитывает уклон, мощность и вес.
**Этап.** 7.
**Критерии приёмки.**
1. Кодек SIM формирует байты по формату из вводного абзаца FRD: уклон 5.00 % → `11 00 00 F4 01 28 14`; −3.00 % → `11 00 00 D4 FE 28 14`; 0 % → `11 00 00 00 00 28 14`; уклон 12.34 % → поле Grade `D2 04`; ветер 1.5 м/с → поле Wind Speed `DC 05`; Crr 0.004 → `28`; Cw 0.20 → `14`. Значения вне диапазона типов (уклон вне ±327.67 %, Crr > 0.0255, Cw > 2.55) кодеком отклоняются. `[авто]`
2. Передаваемый уклон = g(s) трассы в текущей позиции s (D3D-08), умноженный на крутизну FRD-05, округлённый до 0.01 %. Позиция s = интеграл скорости модели за время сессии (по модулю L). `[авто]`
3. Передаваемый уклон ограничивается диапазоном Supported Inclination Range (`0x2AD5`: min, max — sint16 LE, разрешение 0.1 %; increment — uint16), прочитанным после подключения через `read_characteristic(id, 0x1826, 0x2AD5)`; без ответа — диапазоном −10 … +20 %. `[авто]` (запасной диапазон предложен, подтвердить)
4. Ограничение частоты: команда `0x11` уходит не чаще одного раза в 1 с и только если передаваемый уклон отличается от последнего отправленного не меньше чем на 0.1 %; при езде 10 мин по трассе «горы» на `FakeTrainer` число команд `0x11` ≤ 600, между любыми двумя соседними ≥ 1000 мс. `[авто]` (частота и порог предложены, подтвердить)
5. Задержка: при въезде на участок с новым уклоном (изменение ≥ 0.1 %) команда уходит не позже 1 с после того, как позиция s пересекла границу участка (аналог NFR-01). После переподключения станка (DEV-08), возобновления после паузы и при старте сессии текущий уклон отправляется не позже 1 с, независимо от порога п.4. `[авто]`
6. Перед использованием SIM проверяется поддержка: в Fitness Machine Feature (`0x2ACC`) установлен бит «Indoor Bike Simulation Parameters Supported» Target Setting Features; если бит не установлен или станок отвечает на `0x11` кодом результата ≠ `0x01`, сессия переходит на фиксированное сопротивление (FRD-05.4) и пользователь видит сообщение «станок не поддерживает SIM». `[авто]` (правило предложено, подтвердить)
7. Модель скорости с уклоном (вводный абзац FRD): v(P, m, g) монотонно растёт по P, убывает по g; на подъёме (g > 0) убывает по m. Опорные значения при 75 кг: 200 Вт, 0 % → как D3D-02.2 (34 ± 3 км/ч); 200 Вт, 5 % → 15.2 ± 1.5 км/ч; 200 Вт, 10 % → 8.4 ± 1.0 км/ч; 0 Вт, −5 % → установившаяся 49.8 ± 3 км/ч. Ограничение изменения за сэмпл и торможение — как D3D-02.3–4. `[авто]` (опорные значения выведены из модели, допуски предложены, подтвердить)
8. Модель скорости использует полный уклон трассы g(s), а не уклон, сниженный крутизной FRD-05 (крутизна влияет только на нагрузку станка). `[авто]` (правило предложено, подтвердить — открытое решение 32)
9. Источник скорости в свободной езде — модель (`speed_source = модель`), а не скорость станка: позиция на трассе, дистанция и уклон, отправляемый станку, согласованы между собой. `[авто]` (правило предложено, подтвердить — открытое решение 33; отличие от В-8)
10. На Tacx Neo в подъём ощутимо тяжелее, на спуске легче; смена ощущается не позже 1–2 с после смены уклона в сцене. `[ручная проверка]`

### REQ-FRD-05 — Крутизна SIM и фиксированное сопротивление на лету
**Формулировка.** Настройка крутизны SIM (доля уклона, передаваемая станку, 0–100 %) и переключение на фиксированное сопротивление на лету.
**Этап.** 7.
**Критерии приёмки.**
1. Крутизна k задаётся от 0 до 100 % с шагом 5 %, по умолчанию 50 %, сохраняется в профиле между сессиями. Передаваемый уклон = g(s) × k / 100: при g = 8 % и k = 50 % уходит 4.00 % (`… 90 01 …`), при k = 0 % — 0 %, при k = 100 % — 8.00 %. `[авто]` (шаг и значение по умолчанию предложены, подтвердить — открытое решение 32)
2. Крутизна применяется одинаково к подъёмам и спускам: при g = −4 % и k = 50 % уходит −2.00 %. `[авто]` (правило предложено, подтвердить — открытое решение 32)
3. Изменение крутизны во время езды отправляет новый уклон не позже 1 с, даже если позиция на трассе не изменилась (обходя порог FRD-04.4, но не чаще 1 раза в 1 с). `[авто]`
4. Одно действие переключает SIM ↔ фиксированное сопротивление: при переходе на фиксированное не позже 1 с уходит Set Target Resistance Level с уровнем пользователя по правилу WRK-04.2 (тот же уровень и то же отображение процентов), после чего команд `0x11` нет до обратного переключения; при возврате в SIM не позже 1 с уходит `0x11` с текущим уклоном. Изменение уровня в фиксированном режиме — как WRK-04.2. `[авто]`
5. Переключение режима и изменение крутизны не останавливают таймер, не прерывают запись потоков и не меняют позицию на трассе; модель скорости в фиксированном режиме продолжает учитывать уклон (п.8 FRD-04). `[авто]`
6. Текущий режим (SIM/фиксированное) и крутизна видны на HUD свободной езды; каждое переключение записывается событием заезда (как переключения ERG, LOC-01.4). `[авто]`
7. На Tacx Neo изменение крутизны и переключение режима ощущаются при педалировании. `[ручная проверка]`

### REQ-FRD-06 — HUD свободной езды
**Формулировка.** HUD свободной езды: мощность, пульс, каденс, скорость, дистанция, время, текущий уклон; профиль высот трассы с позицией гонщика; график мощности и пульса за прошедшее время.
**Этап.** 7.
**Критерии приёмки.**
1. Показываются: сглаженная мощность (HUD-09), пульс, каденс, скорость, прошедшее время в форматах HUD-05.1; дистанция — км с двумя знаками (накопленная за сессию, не по модулю круга); текущий уклон трассы g(s) — % с одним знаком и знаком «−» на спуске. Отсутствующее значение — «—». Целевой мощности, обратного отсчёта и списка интервалов нет. `[авто]` (формат дистанции предложен, подтвердить)
2. На HUD показывается уклон трассы g(s), а не уклон, переданный станку (крутизна его не меняет). `[авто]` (правило предложено, подтвердить)
3. Профиль высот трассы — та же серия, что в превью FRD-03.3; маркер гонщика стоит на x = (s mod L) / L × ширина (±1 px) и на высоте профиля в этой точке; после полного круга маркер возвращается к левому краю. `[авто]`
4. График мощности и пульса за прошедшее время подчиняется правилам HUD-11 (линия факта, разрывы, прореживание) и HUD-12 (пульс — красная линия без заливки, своя шкала) без профиля плана. Ось X — скользящее окно последних 20 мин (до 20 мин — от 0 до 20 мин); ось Y мощности — от 0 до max(1.25 × FTP, максимум сглаженной мощности в окне). `[авто]` (окно и шкала предложены, подтвердить — открытое решение 34)
5. Цифры подчиняются HUD-14; раскладка — панель цифр сверху, график внизу во всю ширину, центр кадра свободен (HUD-13.1, 13.4–13.6 без списка интервалов); место профиля высот — по решению game-designer. `[авто]`
6. На снимках HUD свободной езды на подъёме и на спуске трассы «горы» видны все цифры п.1 с единицами, уклон со знаком, профиль трассы с маркером гонщика в правильном месте подъёма, линии мощности и пульса. `[визуальная проверка]`

### REQ-FRD-07 — Езда без лимита, ручное завершение, сохранение и Strava

Декодированные значения совпадают с сэмплами: дистанция ±0.01 м, высота ±0.2 м, `total_ascent` — с набором п.4 ±1 м. `lap` — по одному на каждый полный круг трассы плюс неполный последний (вместо шагов плана). `[авто]` (разбиение на lap предложено, подтвердить)

### REQ-NFR-01 — Задержка смены нагрузки ≤ 1 с

32. **Крутизна** (FRD-05): по умолчанию 50 % (как trainer difficulty в Zwift) или 100 %; шаг 5 %; применяется ли одинаково к подъёмам и спускам (предложено — да) или спуски всегда передаются полностью/обнуляются; модель скорости и уклон на HUD — по полному уклону трассы, а не по сниженному крутизной (предложено — да).
33. **Источник скорости в свободной езде** (FRD-04.9): предложено — всегда модель с уклоном (позиция на трассе и уклон для станка должны быть согласованы), в отличие от В-8 для тренировки по плану, где берётся скорость станка. Подтвердить.
34. **Детали свободной езды** (FRD-01.4, FRD-02.3, FRD-06, FRD-07): можно ли запустить свободную езду без подключённого станка (только в режиме разработки на `FakeTrainer`, или всегда с «нулевой» мощностью); пауза в свободной езде — как WRK-05/В-4; трасса по умолчанию — последняя выбранная, при первом запуске равнина; график мощности и пульса — скользящее окно 20 мин; дистанция — км с двумя знаками; `lap` в FIT — по кругу трассы; название в Strava — «Свободная езда — <трасса>».
35. **Инструмент снимков экранов** (`[визуальная проверка]` HUD-10..14, FRD-03/06, D3D-08.8, UIX-01..05): текущий `./scripts/screenshot.sh` снимает только 3D-мир без HUD и без выбора трассы. Для приёмки нужны снимки экрана тренировки с HUD в заданных состояниях (начало/середина/последний интервал), HUD свободной езды на подъёме/спуске, каждой из четырёх трасс, экранов меню в разрешениях UIX на ru и en. Вопрос менеджеру — завести задачу на расширение инструмента (не требование продукта).
36. **Визуальная система меню** (UIX-01..05): нет спецификации game-designer (`docs/game/design.md` отсутствует) — палитра, шрифты, размеры, отступы, стили кнопок/карточек/списков, состав групп настроек; до неё визуальная проверка UIX сводится к согласованности экранов между собой. Также подтвердить: минимальная цель нажатия 44 × 44 pt / 48 dp; набор разрешений (телефон 390×844 и 844×390, планшет 1024×1366 и 1366×1024, компьютер 1280×720 и 1920×1080); поддерживаемые ориентации — меню на телефоне в портретной и альбомной, экран тренировки только в альбомной?; ключевые цифры карточки плана — длительность и максимальная цель (TSS/IF не считаем — собственная аналитика вне MVP); основные кнопки главного экрана не меньше чем вдвое крупнее прочих.

### Решения менеджера по вопросам В-1..В-9 (`docs/backlog.md`, раздел 5) — подтвердить владельцу
Решения приняты главным менеджером, чтобы не блокировать разработку; внесены в REQ с пометкой «(решение менеджера, подтвердить владельцу)». Владелец может отменить любое — тогда критерии правятся.

- **В-1** (PRF-02, HUD-04): поле профиля `max_hr`, валидация 100–220, по умолчанию пусто → зоны пульса недоступны, HUD-04 показывает «—»; зоны пульса по умолчанию — 5 зон от max HR (60/70/80/90 %), переопределяются вручную или из Intervals.icu.
- **В-2** (контракт моста, DEV-07, WRK-04, NFR-06): операция `read_characteristic(id, service_uuid, char_uuid)` с асинхронным ответом `characteristic_read(id, char_uuid, bytes)`; используется для Battery Level `0x2A19` и Supported Resistance Level Range `0x2AD6`.
- **Н-3** (вводный абзац DEV, DEV-01, 02, 06, 07, 08, 09, NFR-01, NFR-06): имена контракта моста согласованы с кодом `src/devices/ble/ble_bridge.gd` (`connect_peripheral`/`disconnect_peripheral`, `notification`, `write_done`, `error`, `discover_services`/`services_discovered`, `get_adapter_state`/`is_available`/`adapter_state_changed`); нативный класс `OvoschBle`, обёртка `NativeBleBridge`, заглушка `StubBleBridge`, выбор — `BleBridge.create_default()`. Код не переименовывается: `connect`/`disconnect` заняты `Object` в Godot.
- **Н-2** (NFR-06.3): слои `src/session/` и `src/app/` признаны допустимыми с правилами зависимостей, зафиксированными в CLAUDE.md.
- **В-3** (LOC-01..07): **отклонение от ТЗ (SQLite)** — для MVP файловое хранилище за интерфейсом `RideRepository` (каталог заезда: `meta.json` + бинарные потоки); SQLite — допустимая реализация того же интерфейса позже; критерии через интерфейс, не через SQL.
- **В-4** (WRK-05): на паузе ничего не посылается на станок (цель — последняя отправленная), телеметрия не пишется, время паузы не идёт в elapsed; при возобновлении цель отправляется повторно.
- **В-5** (INT-06): зоны мощности из Intervals.icu — список границ в ваттах любого количества (1–9), маппинг в `PowerZones` с пользовательскими границами; зоны пульса — из `sportSettings`, если есть, иначе от `max_hr`; локальное переопределение в приоритете.
- **В-6** (STR-01): `client_id`/`client_secret` не в репозитории — из `user://secrets.cfg` или переменных окружения в dev-сборках, для магазинных — из конфигурации сборки вне репо; redirect на macOS/Linux/Windows — loopback `http://127.0.0.1:<port>/callback` через встроенный временный HTTP-сервер, на iOS/Android — `ovoschrider://strava`; альтернатива для владельца — серверный обмен кода без секрета в клиенте.
- **В-7** (D3D-05): замер draw calls — `[ручная проверка]`; в `[авто]` — бюджет узлов/материалов сцены и статическая проверка отсутствия аллокаций в per-frame коде.
- **В-8** (WRK-08, LOC-01, LOC-05, STR-02): источник скорости — FTMS Indoor Bike Data, если станок её даёт, иначе расчёт по модели D3D-02; `speed_source` фиксируется в метаданных заезда.
- **В-9** (INF-03): проверка истории коммитов в CI требует `fetch-depth: 0` в `actions/checkout` — добавлено как критерий.
- **В-10** (WRK-02.5, IMP-01.2): на шаге FreeRide при включённом ERG станок переводится в режим сопротивления (`set_erg_enabled(false)` + `set_resistance_level(уровень пользователя)`) не позже 1 с после начала шага; на следующем шаге с целью ERG возвращается (`set_erg_enabled(true)` + цель) в ту же секунду; переключатель ERG на HUD остаётся «вкл» — это режим шага, не выбор пользователя. Причина: по прежней формулировке станок держал цель предыдущего интервала, и «свободная езда» не была свободной (наблюдение tester'а).
- **Уточнение DEV-08.3** (наблюдение tester'а, приоритет В-4): при обрыве и восстановлении на паузе цель уходит при `resume`, а не ≤ 1 с после `connected`; после `connected` на паузе — только Request Control.
- **В-11** (WRK-04.2, DEV-02.5): Set Target Resistance Level — uint8 в единицах 0.1 (макс 25.5), а диапазон `0x2AD6` — sint16 (Tacx Neo 0..100.0); проценты 0–100 отображаются на кодируемый поддиапазон `[max(min,0); min(max,25.5)]` с привязкой к `increment`, 100 % → максимум кодируемого, при `max` > 25.5 — одно предупреждение в лог; без `0x2AD6` — линейно 0..100 % → 0..25.5 (ранее было 0..10.0). Числа: 50 % → 12.8 (`04 80`), 100 % → 25.5 (`04 FF`).
